Upgrading to Mel Spectrograms
If we were to upgrade the prosody analysis from an 8-feature vector to a full mel spectrogram, the implications would be significant, offering a massive increase in data richness at the cost of much higher complexity.

A mel spectrogram is a 2D image that represents how the spectrum of frequencies in the audio signal changes over time, scaled to human perception. Instead of 8 numbers, you get a rich visual texture of the user's voice.

The Architectural Impact:
Richer Data, Deeper Insight: A spectrogram captures nuance that simple features miss—the subtle wavering in a voice, the rich harmonic content of a laugh, the flatness of a depressive tone. It's the difference between seeing a stock ticker ([pitch: -0.5, energy: -0.8]) and seeing a detailed chart of market sentiment. The AI could learn to recognize incredibly subtle, non-verbal emotional cues directly from the "image" of the voice.

Increased Model Complexity: You can't just feed a 2D image into the same models.

The IPIPAnalyst's PersonalityPredictor would need to be upgraded. Instead of a simple nn.Linear layer, it would need a Vision Transformer (ViT) or a Convolutional Neural Network (CNN) front-end to process the spectrogram image before combining it with the text embedding.

Significant Computational Overhead: Processing a full spectrogram for every turn is far more computationally expensive than calculating 8 scalar values. This would add noticeable latency to the real-time interaction loop.

Data-Hungry Training: A model that can interpret the subtle patterns in a spectrogram requires vastly more training data. The "100k synthetic samples" you planned for the IPIPAnalyst might need to be an order of magnitude larger to effectively train a ViT or CNN to correlate visual voice patterns with IPIP facets.

Verdict: Upgrading to mel spectrograms is a powerful future-state enhancement. It would be a Phase 5 or 6 task. It's better to build a fast car with a good-enough engine before trying to swap in a Formula 1 powertrain.

# app.py - A simple Gradio Companion App for the Samantha Protocol

import gradio as gr
import requests
import base64
import os
from datetime import datetime

# --- Configuration ---
# This should point to your deployed Samantha API on RunPod
SAMANTHA_API_URL = os.getenv("SAMANTHA_API_URL", "http://localhost:8000")
USER_ID = "samantha_user_1" # Hardcoded for our single-user setup

def handle_interaction(audio_filepath, chat_history):
    """
    Called when the user records audio. It sends the audio to the Samantha API,
    gets the response, and updates the chat history.
    """
    if audio_filepath is None:
        return chat_history, None

    try:
        # 1. Read the audio file and encode it
        with open(audio_filepath, "rb") as f:
            audio_bytes = f.read()

        # 2. Send the audio to the Samantha backend
        response = requests.post(
            f"{SAMANTHA_API_URL}/api/v1/interact",
            files={"audio_file": ("recording.wav", audio_bytes, "audio/wav")},
            data={"user_id": USER_ID}
        )
        response.raise_for_status()
        response_data = response.json()

        # 3. Add user's (transcribed) turn and AI's turn to chat history
        # The API doesn't return the user transcript, so we'll just note it was an audio input
        # A more advanced version could do client-side transcription for the UI
        chat_history.append(("[Your Audio Input]", None))
        chat_history.append((None, response_data.get("response_text")))
        
        # We return the interaction_id to be stored in a hidden state for feedback
        return chat_history, response_data.get("interaction_id")

    except requests.exceptions.RequestException as e:
        gr.Warning(f"API Error: {e}. Is the Samantha backend running?")
        return chat_history, None
    except Exception as e:
        gr.Error(f"An unexpected error occurred: {e}")
        return chat_history, None

def handle_feedback(interaction_id, rating):
    """
    Called when a user clicks a rating slider. Sends the feedback to the API.
    """
    if not interaction_id or rating == 0:
        # Don't send feedback if there's no interaction or rating is neutral
        return
        
    try:
        feedback_payload = {
            "interaction_id": interaction_id,
            "feedback_score": int(rating)
            # A more complex UI could have sliders for these other values
            # "emotional_resonance": 0.5,
            # "surprise_level": 0.5,
            # "significance_score": 0.5
        }
        
        response = requests.post(
            f"{SAMANTHA_API_URL}/api/v1/feedback",
            json=feedback_payload
        )
        response.raise_for_status()
        
        gr.Info(f"Feedback ({rating}/5) submitted for last interaction!")

    except requests.exceptions.RequestException as e:
        gr.Warning(f"Could not submit feedback: {e}")
    except Exception as e:
        gr.Error(f"An unexpected error occurred while submitting feedback: {e}")


# --- Gradio UI Definition ---
with gr.Blocks(theme=gr.themes.Soft(), title="Samantha Companion") as app:
    
    # Hidden state to store the ID of the last interaction for feedback
    last_interaction_id = gr.State(None)
    
    gr.Markdown("# Samantha")
    gr.Markdown("Your always-on relational AI companion. Speak to interact.")

    # The main chat interface
    chatbot = gr.Chatbot(label="Conversation", bubble_full_width=False, height=600)
    
    # The audio input widget
    audio_input = gr.Audio(sources=["microphone"], type="filepath", label="Speak Here")

    # The feedback slider
    with gr.Row():
        feedback_slider = gr.Slider(
            minimum=1, 
            maximum=5, 
            step=1, 
            label="Rate Last Response (1=Poor, 5=Excellent)",
            value=0 # Default to 0, meaning no rating
        )

    # Linking the components
    audio_input.stop_recording(
        fn=handle_interaction,
        inputs=[audio_input, chatbot],
        outputs=[chatbot, last_interaction_id]
    )
    
    feedback_slider.release(
        fn=handle_feedback,
        inputs=[last_interaction_id, feedback_slider],
        outputs=None
    )

if __name__ == "__main__":
    app.launch(server_name="0.0.0.0", server_port=7860)

Can an 8-Feature Prosody Vector Capture Enough Nuance?
This is the central question for the IPIPAnalyst and LinOSS Core.

The Honest Answer: No, it cannot capture the full nuance of human expression, but that's a feature, not a bug, for this architecture.

Its Limitation: The 8 features you've chosen (pitch, energy, tempo, etc.) are a highly compressed, lossy representation of the audio signal. Why It's a Good Starting Point: The limitation is also its strength for a buildable system. This 8-feature vector is a pragmatic compromise that captures about 80% of the useful paralinguistic signal for about 20% of the computational cost.
